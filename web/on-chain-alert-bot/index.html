On-Chain Alert Bot

Watches Pharos for the conditions in a rules file (a large transfer of a token, or any event on a contract) and sends one alert per event, saying what happened, the value and the explorer link. It never sends the same alert twice.

kinds: large-transfer (token, minAmount) · contract-event (contract, event, involving?)
Sequence · rules.pharos.json · USDC ≥ 100, last 300 mainnet blocksidle · press Run live

    Each lamp lights when the real step returns. Times are measured, not animated.

    Live alerts are delivered to this page: a public button that posts to a real channel would let anyone spam it. The Discord delivery is the recorded run below, with its message ids checked against the chain. Mainnet reads go through the hosted Chain MCP; Atlantic reads go straight to the Atlantic RPC (its Chain MCP runs over stdio, which a web function cannot start).

      What's ours

      Beyond the requirement list

      Rules as data

      Conditions live in a JSON file, not in code: several rules per file, each with its own id and threshold in token units (decimals read from the token). A bad rule is refused with a message that says which field is wrong. Try one above.

      Delivery you can check

      The Discord webhook is called with ?wait=true, so every alert comes back with a message id. Decoding that id gives Discord's own clock, about 3 s after each block. The proof does not rest on a screenshot.

      A lost cursor is not spam

      One alert per rule per txHash:logIndex, kept in a sent-set file apart from the block cursor. Lose the cursor and the same blocks come back, but nothing is sent again; a failed delivery is retried.

      How this was built
      Built with Claude as a coding assistant. The design, the failure cases and the extra feature were chosen by me; the commit history shows the iterations.
